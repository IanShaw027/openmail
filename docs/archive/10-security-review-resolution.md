## 1. 游客操作收码 API（高）

### 风险

在「入库账号对所有访问者可见」模型下，若游客还能：

- 为任意公共账号 **签发** URL  
- **rotate** 掉他人正在用的 URL  
- **delete** 收码接口  

则构成：**读信能力扩散** + **对依赖旧 URL 的脚本 DoS**。

产品又要求游客能「生成/复制收码 API」，不能整段收回。

### 决议（权限分层）

| 操作 | 谁可以 | 说明 |
|------|--------|------|
| **create-or-return**（无则创建、有则返回现有） | 游客 | 满足「一点生成/复制」；**同一记录不重复签发新 token** |
| **rotate**（作废旧 URL、发新 token） | **管理员**，或 **持有当前 token 证明**（body/query 带 `current_token`） | 防止路人轮换搞挂别人脚本 |
| **delete** 收码接口 | **仅管理员** | 破坏性操作 |
| **delete** 服务端账号 | **仅管理员** | 游客只能删本机浏览器缓存账号 |
| 调用收码 URL 取码 | 任意持有 URL 者 | 设计如此；靠 token 熵 + 工程底线 |

> 不强制引入「每账号 manage_secret」作为 MVP；用 **current_token 证明** 覆盖「我丢了链接要换新」的游客场景。  
> 管理员始终可 rotate/delete。

### 残留风险（接受并写进隐私）

只要账号已入库且对全站可见，**任何游客都能 create-or-return 拿到同一收码 URL**，从而读该邮箱验证码。  
这是 **「实例内公共号池」** 的固有模型，不是实现 bug。缓解：

- UI/隐私明确：**保存到服务器 = 本实例所有访问者可见可用**  
- 敏感号只放 **浏览器缓存**，不要入库  
- 部署勿裸奔公网无 HTTPS / 无网络边界

## 2. 无限流 vs 安全需求（高）

### 冲突来源

| 文档 | 说法 |
|------|------|
| 09 / 08 | 限流暂时不做 |
| 01 / 04 | 要限流、防打爆上游 |

GET/POST 均可触发取信 + 无限流 → token 泄露可刷上游、触发风控。

### 决议（拆成两层，消解冲突）

| 层级 | MVP | 含义 |
|------|-----|------|
| **运营限流**（配额、管理台开关、对外 429 产品能力） | **暂不做**（保持 09） | 不要求完整限流产品 |
| **工程安全底线** | **必须做** | 不叫「限流功能」，但是实现硬要求 |

工程底线（Phase 1 必有）：

1. 收码 API 默认 **短缓存优先**（`refresh=0`）；未过期有 code 则不打上游。  
2. **同账号取信串行**（mutex），禁止并发打爆 Cookie 登录。  
3. **最小上游间隔**（如同一 account 默认 ≥ 3–5s 才允许再次 real fetch；可配置，默认开）。  
4. 批量取信 **有限并发**（如 3），与「运营配额」无关。  
5. 实现预留完整限流扩展点，便于以后打开。

文档表述：

- 01：将「限流」改为「收码 token 高熵 + 工程底线；运营限流可后续」  
- 04：并发控制保留；删除「收码 API 每 token 日限额」作为 MVP 必做  
- 09：§8 改为上述两层定义

## 3. HttpApi 与 SSRF（高）

### 结论

**完全成立。** HttpApi 本质是服务端按用户 URL 出站，无 SSRF = 扫内网/打 metadata。

### 决议

HttpApi **首版（Phase 1）必须内置**：

- 仅 `http`/`https`  
- DNS 解析后阻断：私网、loopback、link-local、云 metadata 段等  
- 禁止不安全的 redirect 到内网（**每跳复检**）  
- 可配置域名/IP 白名单（管理员）；默认拒绝内网  

路线图：SSRF 从 Phase 3 **挪到 Phase 1，与 HttpApi 同交付**。

## 4. Cookie 6h 冲突（中）

### 结论

**成立。** 09 已否决 helper 式 6h 硬删；03/07 仍写 6h → 实现易错。

### 决议

统一为 09：

- 注入条件：**有 cookies 即尝试**；以探测是否登录为准  
- **每次成功写回**滚动续期  
- **不做默认 6h 硬过期**  
- 可选 `absolute_max_age`（如 7d，默认可关或很大）仅防无限堆积  

`expires_at` 字段语义改为：可选绝对上限 / cookie 自身过期提示，**不是**默认 6h 业务硬删。

## 5. 加密 Phase 与措辞（中）

### 结论

**成立。** 入库即含 password / refresh_token / cookies → 加密是 MVP 底线，不能 Phase 3「硬化」才做。

### 决议

- 全文：**必须** at-rest 加密（AES-GCM 或等价 + `OPENMAIL_MASTER_KEY`）  
- 路线图：加密进 **Phase 1 Store**，从 Phase 3 删除「才做加密」  
- 02/03 去掉「建议加密」弱表述  

---

## 6. 隐私 vs 公共号池（中）

### 结论

**成立。** 09 是公共实例账号模型；07 仍像「我的私有空间」+「禁止未授权访问账号列表」。

### 决议

对外必须写清：

1. **仅浏览器**：仅本机  
2. **保存到服务器**：**本 OpenMail 实例的所有访问者**可见该账号并可用于取信/（在权限规则下）获取收码 URL  
3. 管理密码保护的是 **系统配置 / 破坏性操作**，不是「游客看不到入库列表」  
4. 07 §6「禁止未授权访问账号列表」改为：  
   - 游客可读实例内入库账号元数据（按产品）  
   - **禁止**未授权访问管理接口与明文凭证字段（列表默认掩码 token/密码）
